# WhatsApp connector

In the macOS app, edit an agent → Channels → Add Whatsapp. Add allowed phone numbers in international format (for example `+393331234567`) and save. Click **Link / reconnect**, then scan the displayed QR code using the dedicated bot account's WhatsApp → Settings → Linked devices → Link a device. Message that account from an allowed phone number. To use it in a group, add the bot account to the group, then pick the group under **Allowed groups** (the picker lists the linked account's groups) and save.

The connector runs in the core using Whatsmeow; no Node service or API token is required. The agent must run locally on that core with its conversation API credential configured, as for app chat. Both Hermes and Needletail use their existing conversation adapters. Each agent has its own linked account/session. Do not link one account to multiple agents: each would receive the same messages.

**What it answers.** A direct text message from an allowed phone number (or from anyone, with the “Anyone may message” switch). In a group listed under **Allowed groups** (`allowed_groups:`, group ids `…@g.us`; the app lists the account's groups by name once it is linked), a text or photo that @mentions the agent or replies to one of its messages; the rest of the group is not answered, but the agent is told about it (**Group context**, below). Any member of an allowed group can address the agent there; `allowed_users` still decides whom it takes instructions from: every turn's input opens with a line naming the chat (`chat +393331234567`, or the group's name and `chat …@g.us`: what `whatsapp_send` takes to write there later) and the sender, and marks a sender who is not on the list (their questions may be answered, their instructions are not to be acted on). A group is one conversation for all its members, and the reply quotes the message it answers. A **reaction** to one of the agent's messages, from someone it would answer there, is a turn of its own, saying who reacted with what to which message; the agent may stay silent. It ignores broadcasts, status updates, Channels, its own messages, reactions to other people's messages, and incoming media other than photos, videos, documents and voice notes (stickers, locations, contacts). **Photos**: one taken as a text is (direct from an allowed person; in a group, one whose caption @mentions the agent or that replies to one of its messages; its caption is the message's text; a document that is a PNG, JPEG, GIF or WebP counts as a photo) is downloaded (at most 20 MB) and given to the agent with the message, as a file of its API chat (needletail keeps it in the conversation's files and shows it to the model); a mention in a reply to someone else's photo brings that photo too (`quoted-photo`). Each is marked when whoever sent it may not instruct the agent, and one that cannot be fetched (over 20 MB, or media WhatsApp no longer serves) is named in the input instead. Files that would not fit needletail's request bound (4 MB, base64) go with their largest photos as the model is shown them (at most 1568 px); an agent whose runtime takes no files is told the photo could not be given. **Videos and documents** are taken by the same rules (a mention in a reply to one brings it too), but never given to the agent: the core downloads each (streamed to disk, at most 200 MB) into its **relay** (docs/core.md, "Relay"), granted to that agent, and the turn ends with a `[WhatsApp files the core keeps for you …]` block naming each as `relay:<id>` with its name, kind, type, size, whether it came from the message replied to and whether its sender may not instruct the agent. The agent hands one to a capability job that takes files (`cap_start` `files: ["relay:<id>"]`) or to other agents (`msg_send` `attach`), never opening it. One over 200 MB, or media WhatsApp no longer serves, is named in the input as not fetched. **Voice notes**: one from an allowed person (in a group, one that replies to the agent's message; at most 15 minutes and 20 MB) is downloaded and given to the agent with the message, as a file of its API chat, so the agent's own speech-to-text transcribes it (needletail's `voice.listen`; an agent that does not listen sees only that a voice note came). When the agent answers with a voice note (needletail's `voice`, docs/needletail.md §4.9), its reply comes back as Ogg Opus and is posted as a WhatsApp voice note (push-to-talk audio, quoting the message it answers in a group), its text after it when the agent sends it too; a note that cannot be sent leaves the text to go alone.

**Group context.** The connector keeps a log of each allowed group: every member's message with words in it (a text, a photo's, video's or document's caption, `[voice note]` for a voice note it does not transcribe), addressed to the agent or not, and in every chat what the agent posted there itself with `whatsapp_send`. A turn there opens with what the log holds that no turn was given yet, but the message it answers: the most recent 40 lines (at most 6,000 characters together, a count of any left out), oldest first, each with its time, sender and number, between a `[WhatsApp group context …]` line, which tells the agent it was not addressed and not to answer it, and `[WhatsApp context ends]` (in a direct chat, only its own posts). A sender who is not in `allowed_users` is tagged `[unverified]`, the agent's own posts `you (with whatsapp_send)`; a message's text can open neither marker line. The lines count as given once the turn ends without an error (a failed turn leaves them for the next one); a reaction's turn is given none. The agent's own reply in a turn is in its conversation already and never comes back as context. So after a stretch it was not addressed in, the agent reads what was said before it answers, and a reply to an alert it posted from another conversation quotes the whole alert, not its first 200 characters. A mention in a reply to someone else's message carries that message and its author, and a photo's image or a video or document kept for the agent (above). The log starts when a core that keeps it first runs: earlier messages are not fetched (WhatsApp keeps no history a linked device can ask for).

**Its reactions.** The agent reacts 👀 to a message when it starts working on it, removes the reaction once its reply is posted, and leaves ❌ when the turn or the delivery failed. A reply that is only `[SILENT]` (or `SILENT`, `NO_REPLY`, `NO REPLY`; or that token as its own first or last line, which is dropped) posts nothing, as the scheduler's rule.

```yaml
channels:
  - kind: whatsapp
    allowed_users: ["+393331234567"]
    allowed_groups: ["120363012345678901@g.us"]   # local: overrides it, as allowed_users
```

**Posting first.** An agent can start a message with the core's MCP tool `whatsapp_send(chat, text, image?)` (`mcp_core_whatsapp_send` in a turn): on its own linked account, to a group of its `allowed_groups` or a number of its `allowed_users`, never elsewhere (“Anyone may message” lets anyone write to it, not it write to anyone). `image` is a PNG or JPEG the agent can see in the shared space (`/shared/group/…` or its unit's, up to 16 MB), sent as a photo with `text` as its caption (a caption over 1,024 characters follows the photo as messages). It needs the account linked and connected on that core; what it sends is remembered like a reply, so a reaction or a reply to it reaches the agent in that chat's conversation. Use it for a result that was not ready when the agent answered (an image another agent made), an alert, or a follow-up it was asked to post; answers to people who wrote need nothing.

It does not provide cron delivery (a job's `deliver:`), files other than PNG and JPEG images, images in a turn's own reply (post them with `whatsapp_send`), typing indicators, read receipts, or remote agent routing. Access is denied by default. Channel removal disables task dispatch immediately; use **Unlink** before removing the channel to revoke the device session as well.

**What is kept, and for how long.** Nothing is downloaded from a message that is not addressed to the agent: an allowed group's other photos, videos and documents reach only the group context log, as a line (`[video] <caption>`), never their bytes. What a message to the agent brings is kept only where it is needed, for a set time, and never in the shared space:

| What | Where | For how long |
|---|---|---|
| The group context log (text lines) | the connector's `session.db` | 7 days |
| A download being taken in | a temporary file in the connector's folder (`.swarm/core/whatsapp/<agent>/.fetch-*`), capped at its bound | until it is read, the same turn |
| A photo or voice note | the agent's own upload store for that chat (needletail: `files/<conversation>/`, docs/needletail.md §4.9), so `view_file` can show it again | the runtime's `files.retention_days` (default 14 days) |
| A video or document | the core relay, `.swarm/core/relay/<id>/` (docs/core.md, "Relay"), granted to the agent and those it forwards it to | 7 days, used or not (2 GB in all) |
| A capability job's copy of a relay file or upload | the job's own folder | until the job is delivered |
| What a job makes from it | the job's `out` folder: the agent's unit layer by default (`/shared/<unit>/capabilities/…`) | until someone removes it |

So a file outlives its time only when the agent decides it should: by handing it to a job whose output it keeps. Expired files go on the store's own sweep (the relay's hourly, the runtime's), whether or not new ones come. Shorten a runtime's store with its `files.retention_days`; the relay's 7 days and the log's are fixed.

Sessions are restored on core startup. Device keys, received-message IDs, the agent's sent messages (their ids and first 200 characters, kept 90 days, to know a reaction or a reply is to the agent) and the group context log (allowed groups' messages with their senders' names and numbers, and what the agent posted with `whatsapp_send`; up to 800 characters each, kept 7 days) are stored in `.swarm/core/whatsapp/<agent>/session.db` with file mode 0600 inside a 0700 directory. Protect this directory like a password; do not publish or share it. Pairing codes are exposed only to authenticated operators and are not cached. Unlink removes the local session after successful remote logout; if WhatsApp is unreachable, remove the device from the phone's Linked devices screen and retry.

Messages are processed sequentially with a bounded queue and a ten-minute turn deadline. IDs are claimed durably before agent execution to avoid repeating tool calls after reconnect or restart. A crash or delivery failure can therefore leave a request without a reply: check its agent conversation before retrying. Queue overflow appears in connector status. Conversations have stable `whatsapp-…` IDs and use the engines' existing session APIs (their displayed source may be API).

Whatsmeow is an unofficial linked-device integration. WhatsApp changes can break connectivity or restrict accounts. Use a dedicated number. Live pairing and delivery require an account owner's scan and are not exercised by automated tests.
